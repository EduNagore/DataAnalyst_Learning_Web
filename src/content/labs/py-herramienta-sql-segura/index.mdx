Cuando un agente de IA recibe una herramienta para consultar datos (por ejemplo, un servidor MCP), el agente es **un usuario más… que puede equivocarse o ser engañado**. La herramienta no puede fiarse de lo que le llega: debe validar, acotar y registrar.

La política (`POLITICA`: tablas permitidas, filas máximas y palabras prohibidas) y una conexión DuckDB con las tablas `customers` y `orders` de 2025 ya están definidas. Implementa:

1. **`limpiar_sql(sql)`** y **`sin_literales(sql)`**.
2. **`validar(sql, politica)`** → `(True, "ok")` o `(False, motivo)`.
3. **`ejecutar_seguro(sql, politica)`** → resultado con `estado`, `motivo`, `filas` y `truncado`.
4. **`registrar(auditoria, usuario, sql, resultado)`** → entrada de auditoría con el hash de la consulta.

Resultado esperado: pasan las consultas de solo lectura (con CTE, JOIN, comentarios o literales como `'delete me'`); se rechazan `SELECT 1; DROP TABLE customers`, `DELETE`, `COPY`, `ATTACH`, `read_csv('/etc/passwd')` o una tabla fuera de la lista; y `SELECT * FROM customers` devuelve 1.000 de las 60.000 filas, marcado como truncado.

**Límite importante**: esta validación por texto es una primera barrera, no la única. En producción la defensa real es **un rol de base de datos de solo lectura con permisos mínimos**; el filtro lo complementa.
